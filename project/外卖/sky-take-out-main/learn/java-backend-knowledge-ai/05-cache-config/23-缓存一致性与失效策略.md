# 23 缓存一致性与失效策略

## 1. 问题是什么

当同一份菜品或套餐数据同时存在于 MySQL 和 Redis 时，修改数据库后旧缓存仍可能被读到。缓存一致性不是让两份数据每一刻完全相同，而是明确更新顺序和最终一致策略。

## 2. 项目中的处理

管理端修改菜品后会清理缓存：

```java
cleanCache("dish_" + dishDTO.getCategoryId());
```

修改套餐时通过：

```java
@CacheEvict(cacheNames = "setmealCache", allEntries = true)
```

用户下一次查询缓存未命中，就会从数据库读取新数据并重新写入。

## 3. 当前使用的模式

```text
读：缓存命中 -> 直接返回
读：缓存未命中 -> 查 MySQL -> 写 Redis -> 返回
写：更新 MySQL -> 删除 Redis
```

这是常见的 Cache-Aside 模式。删除缓存而不是直接更新缓存，通常可以减少复杂的重复组装逻辑。

## 4. 需要观察的边界

- 数据库更新成功但缓存删除失败，会短时间读到旧数据。
- 并发读写可能出现旧值回填。
- `keys("dish_*")` 适合示例环境，大量 Key 下可能阻塞 Redis，应考虑 `SCAN`。
- 缓存清理范围必须覆盖受影响的所有 Key，例如分类变化可能影响多个分类缓存。

## 5. 学习练习

为菜品更新设计“先删缓存、更新数据库”和“先更新数据库、再删缓存”两种方案，模拟并发读请求，比较数据风险和补偿方式。
